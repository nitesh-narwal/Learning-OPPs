🎯 KEY PRINCIPLES TO REMEMBER

1. START WITH PRIVATE
   Make things private by default, expand if needed

2. PUBLIC = CONTRACT
   Once public, hard to change without breaking clients

3. ENCAPSULATION IS KEY
   Hide implementation, expose interface

4. USE GETTERS/SETTERS
   Gives flexibility to change implementation

5. PROTECT YOUR DATA
   Validate in setters, not in callers

6. INHERITANCE NEEDS PROTECTED
   For methods meant to be overridden

7. DEFAULT FOR PACKAGE UTILITIES
   Internal tools shared only within package

❓ FREQUENTLY ASKED QUESTIONS

Q: Why do I need private if I can just not access it?
A: The compiler enforces it. You get compile error if you try to access
   private members from outside. It's intentional restriction.

Q: Can I use protected instead of private?
A: You can, but it's not secure. Subclasses can modify protected fields.
   Private is stricter and better for internal state.

Q: What's the difference between default and protected?
A: DEFAULT allows same-package access only.
   PROTECTED allows different-package subclass access.

Q: Can I make a top-level class private?
A: No. Top-level classes can be public or default only.
   Only inner classes can be private.

Q: Should I always use getters/setters?
A: Yes for production code. Gives flexibility to add logic later
   without changing client code.
